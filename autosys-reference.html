JOB SCHEDULING — REFERENCE NOTES

Autosys

An automated job control system for scheduling, monitoring, and reporting — built to run thousands of interdependent jobs across UNIX, Windows, and mainframe systems.

Overview

Autosys is a scheduling tool used to control large volumes of jobs across heterogeneous systems. Because it is a dedicated job-control product rather than a general-purpose timer, it supports starting conditions, dependencies, and batch processing that simple schedulers cannot express. Autosys can be operated through both a GUI and a command-line interface.

Autosys vs. Crontab

CRONTAB

  • Built into Unix
  • Schedules using five parameters: minute, hour, day of month, month, day of week
  • No native concept of dependencies between jobs

AUTOSYS

  • Dedicated scheduling tool, not tied to one OS
  • Controls thousands of jobs across UNIX, Windows, and mainframes
  • Supports starting conditions, dependencies, and batch processing

Architecture

Autosys is built from three components that pass job information from storage, to scheduling logic, to execution on the target machine.

Event ServerStores all job data
→
Event ProcessorPolls every 5 sec, dispatches ready jobs
→
Remote AgentExecutes the job, reports back

The event processor connects to the event server roughly every five seconds to check which jobs are ready to run, then hands the job off to a remote agent on the client machine. The remote agent executes the command as defined and reports the result back to the event server.

Job Types

Command job

A single command or executable — a Windows batch file, or a Unix/PowerShell/shell script.

Box job

A container for a set of jobs, used to organize and control process flow. A box can contain other boxes.

File watcher job

Watches for the appearance of a specific file on the server.

JIL File

JIL — Job Information Language — defines every attribute of a job. A JIL file is deployed to the Autosys server from the command line with:

jil < jil_file_name

Sample structure

insert_job:
job_type:
box_name:
command:
machine:
run_days:
start_time:
condition:
description:
std_out_file:
std_err_file:
alarm_if_fail:
max_run_alarm:
min_run_alarm:
profile: /home/variables_autosys
include_calendar:
exclude_calendar:

Job States

StateMeaning
INACTIVENot yet processed — never run, or taken off-ice/off-hold and awaiting its starting conditions.
ACTIVATEDThe job's top-level box is running, but this job hasn't started yet. Seen only for jobs inside a box.
STARTINGThe event processor has told the remote agent to start the job; about to move to RUNNING.
RUNNINGThe job is executing. For a box job, this means its contents may now start; for a command or file watcher job, the process is actually running.
SUCCESSExit code at or below the "maximum exit code for success" (default: 0). For a box, all jobs inside finished SUCCESS, or the box's success condition evaluated true.
FAILUREExit code above the success threshold (default: any nonzero code). Autosys raises an alarm.
TERMINATEDKilled while RUNNING — by a KILLJOB event, a failed parent box, exceeding max run time, or a manual kill. Not the same as FAILURE. Autosys raises an alarm.
RESTARTCould not start due to a hardware or application problem; scheduled to restart.
QUE_WAITAll starting conditions are met, but no machine resources are available yet.
ON_HOLDHeld — will not run until it receives JOB_OFF_HOLD.
ON_ICERemoved from all conditions and logic — effectively deactivated — until it receives JOB_OFF_ICE.

On Hold vs. On Ice

Both states stop a job from running, but they behave differently once dependent jobs and starting conditions come into play.

ON HOLD

  • Dependent jobs are affected — they wait for this job to finish before running.
  • Taking a job off hold: if starting conditions are already met, it runs immediately.

ON ICE

  • Dependent jobs are not affected — they can run without waiting on this job.
  • Taking a job off ice does not start it, even if conditions are already met — it waits for conditions to occur again.

Events & Options

EventEffect
StartStarts the job if dependency conditions are met. Ignores date/time conditions but not job dependencies. Avoid on jobs inside boxes.
Force StartStarts the job regardless of whether starting conditions are met.
KillStops the job while it is running.
On HoldPlaces the job on hold. Cannot be applied while STARTING or RUNNING.
Off HoldReleases the hold; the job starts if its conditions are met.
On IceDeactivates the job. Cannot be applied while STARTING or RUNNING.
Off IceReactivates the job definition; it starts next time conditions are met.
Send EventChanges job status, priority, or adds a comment.
Cancel EventCancels a recent event issued through Send Event.

CLI Commands

Status & definition

# Check status of a job
autorep -J <NAME OF JOB>

# View job definition / JIL
autorep -J <NAME OF JOB> -q

# View previous runs
autorep -j <NAME OF JOB> -r -n <number of runs>

Controlling jobs

# Start a job
sendevent -E START_JOB -J <NAME OF JOB>

# Force start a job
sendevent -E FORCE_START_JOB -J <NAME OF JOB>

# Kill a job
sendevent -E KILL_JOB -J <NAME OF JOB>

# Put a job on hold
sendevent -E JOB_ON_HOLD -J <NAME OF JOB>

# Take a job off hold
sendevent -E JOB_OFF_HOLD -J <NAME OF JOB>

# Put a job on ice
sendevent -E JOB_ON_ICE -J <NAME OF JOB>

# Take a job off ice
sendevent -E JOB_OFF_ICE -J <NAME OF JOB>

# Change job status (e.g. to SUCCESS)
sendevent -E CHANGE_STATUS -S SUCCESS -J <NAME OF JOB>

Dependencies

# Check dependencies on a job
job_depends -c -w -J <NAME OF JOB>
